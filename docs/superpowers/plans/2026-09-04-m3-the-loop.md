**Unlocks:** demo moments 6 (ROI, closed loop) and 7 (the copilot)
**Builds:** Attribution Engine · Cost ingestion · ROI screen · Insight Engine (fixed
finding set) · Copilot over the event store and registry, proposing spec diffs and

plan records only the decisions the spec leaves open, because those are what a reviewer

## Task 1 — Metric predicates (`core/src/metrics/`)

`metrics:` is a *different language* from `routing.when`. Routing evaluates over a
single lead's score; a metric evaluates over that lead's **event history**.

Grammar, deliberately small and non-evaluating (same reasoning as `evaluatePredicate` —
specs are authored data, and `eval` would put RCE in the read path):

```
metric    := aggregate | boolean
aggregate := ("sum"|"count"|"avg") "(" Type "." field [ "where" cond ] ")"
boolean   := Type "exists"
           | Type "." field OP literal
           | Type "." field "in" "[" literal, ... "]"
           | boolean ("AND"|"OR") boolean
```

Two metric *kinds*, and conflating them is the trap:

- **boolean** — per lead, true or false. Aggregates as a **count of leads**.
- **aggregate** — per lead, a number. Aggregates as a **sum over leads**.

`qualified_lead` counts leads; `revenue` sums rupees. A single evaluator returning
`number` would make `sum(revenue)/count(leads)` silently wrong.

**Unknown event type in a metric is a parse error, not a false.** A typo'd
`Routed.desicion` that quietly evaluates false would under-report conversion forever.
Fold this into `lintSpec` so it is caught at publish.

**Steps**
1. `parseMetric(expr) -> MetricAst` — throws on anything outside the grammar
2. `evaluateMetric(ast, events) -> boolean | number`
3. `metricKind(ast) -> "boolean" | "aggregate"`
4. Extend `lintSpec`: unknown event type, unknown field shape, unparseable metric
5. Tests: all four reference metrics; the typo case; `in` sets; `where` filters

## Task 2 — Cost ingestion + Attribution fold (`intelligence/src/attribution/`)

**Cost model.** Ad platforms report spend per campaign/creative per day, not per lead.
The spine requires a `leadId` on every event, so `CostIngestor` takes campaign-level
spend rows and **allocates evenly** across that campaign's leads in the window, emitting
one `CostObserved` per lead. Even allocation is an assumption and is labelled as one on
the screen — the alternative (a weighted model) is a modelling choice the customer should
make, not one we should bury.

Two cost kinds, because this product's ROI story needs both:

| kind | source | why it matters |
|---|---|---|
| `media` | ad spend, allocated | the denominator the CMO already knows |
| `model` | tokens × price, per conversation | what *this* product adds, and the number a CFO will ask for |

`model` cost comes from the runtime's `response.usage`, so this task also wires usage
reporting — which retires the estimated token figures in the spec.

**Attribution dimension:** campaign → creative → journey version.

**Which version owns a lead?** Events carry a version each and a lead can span
versions. Attribute to the version on the `Routed` event — the version that actually did
the work — falling back to `LeadIngested`. Documented in the fold, surfaced in the API.

**Steps**
1. `CostIngestor.ingestMedia(rows)` — even allocation, idempotent per (campaign, day)
2. `recordModelCost(store, ctx, usage)` — called from the runtime
3. `AttributionEngine.roll(journey)` → rows at each level of the hierarchy
4. Derived: cost per lead / per qualified / per conversion, ROAS, margin
5. Tests: fold arithmetic, version attribution, zero-denominator guards

## Task 3 — Insight Engine (`intelligence/src/insights/`)

All seven finding types from §11.2. Each finding carries `n` and, where it is a
comparison, a **confidence interval from the existing paired bootstrap**. A finding
without support is noise, and noise in front of a CMO is worse than silence:

- minimum support per side (`MIN_SUPPORT = 30`), else the finding is suppressed
- comparison findings state the CI; if it spans zero the finding is not emitted
- every finding carries `severity` and, where one exists, a **suggested spec change**

`policy_friction` degrades to "not enough `PolicyEvaluated` events" rather than
fabricating a finding when the runtime has not emitted any.

**Steps**
1. `Finding` type: code, claim, numbers, n, ci?, severity, suggestion?
2. Seven detectors, each a pure function over folded lead states
3. `insights(scope) -> Finding[]`, ranked by severity then effect size
4. Tests per detector, including the suppression paths

## Task 4 — Copilot (`intelligence/src/copilot/`)

`ask(question) -> Answer + ProposedDiff? + View?`

**Tools over read models, never raw SQL.** SQL from a model is both an injection surface
and a hallucination surface; the tools are the same folds the console uses, so the
copilot and the screens cannot disagree.

| tool | returns |
|---|---|
| `attribution` | the fold from Task 2 |
| `insights` | findings from Task 3 |
| `cohort(dimension)` | conversion broken down by an evidence field or campaign |
| `read_spec` | the YAML for a version |
| `propose_diff` | a validated spec edit |

**The gate that matters:** `propose_diff` runs `parseSpec` + `lintSpec` **before**
returning. An invalid diff is handed back to the model as an error to retry, never to
the user. The copilot therefore cannot propose a journey that would not publish.

**Views are descriptors, not markup** — `{kind: "bar"|"table", title, series}`. The
console renders them. A model emitting HTML into the console DOM is an XSS hole; a
model choosing a chart type from a closed set is the conversational-rendering thesis
without the hole.

**Steps**
1. `View` and `Answer` types; the closed set of view kinds
2. Tool implementations over the folds
3. `Copilot.ask()` — OpenAI tool-calling loop, `modelFor("copilot")`
4. `offlineCopilot()` — keyword routing to the same tools, labelled as offline
5. Tests: diff gate rejects an invalid proposal; view kinds are closed; tools are pure

## Task 5 — API + console

Routes: `GET /api/roi`, `GET /api/insights`, `POST /api/copilot/ask`.
Validation with explicit constraints and the existing `statusFor` split; error bodies
in the standard shape.

Console gains **ROI** and **Copilot** tabs. ROI keeps the observed/modelled distinction
that M1 established — media cost is observed, allocation is modelled.

## Task 6 — End to end

`npm run roi` seeds spend, folds attribution, prints the ROI table and the findings,
then asks the copilot the demo question and prints the answer, the view and the diff.
Spec updated: decision log rows for the metric grammar, the cost model and the diff gate.
